# Packages

Shipped content is usually packed into a few large **archive files** ("packages", "paks") instead of thousands of
small loose files.

## Why pack

- **Opening files is expensive.** Each open costs a system call, permission checks and, on Windows, often an
  antivirus scan. One open followed by many reads is much faster than many opens. Consoles and hard drives make
  the difference larger.
- **Placement on disk.** Files used together (one level's assets) can be stored next to each other, so loading them
  is one sequential sweep instead of jumping around the disk.
- **Fewer, larger downloads and installs,** and integrity checks per archive.

## Layout

```
+--------+---------------------------------------------+-------------------------+
| header | entries (data, each compressed on its own)  | index                   |
+--------+---------------------------------------------+-------------------------+
                                                         name -> offset, size, compressed size,
                                                                 compression method, hash
```

- The **index** is read once (often memory-mapped); finding a file is a lookup, not a search.
- Each entry is **compressed on its own**, so any file can be read without decompressing the others. Large entries
  are split into **fixed-size blocks** (e.g. 64 KB), so a range inside a big file can be read without decompressing
  all of it ([Streams and formats](05-streams-and-formats.md)).
- Different groups can use different **compression**: fast to decompress for things loaded during play, smaller
  for things loaded once.

## File ordering

Recording which files a play session actually loads, in which order, and laying archives out in that order makes
loading mostly sequential. This **file ordering** list is generated by tools and kept as data ([Assets](09-assets.md)).

## Patching, downloadable content and mods

New archives are mounted **above** old ones in the VFS search order ([The virtual file system](02-virtual-file-system.md)):
an updated file in `patch-02.pak` hides the original in `content.pak`. Updates download only the archives that
changed, and the originals stay untouched and verifiable.

## Integrity and protection

- **Hashes** per entry or per block detect corruption (a bad download, a failing disk) before corrupt data reaches a
  loader.
- **Signatures** detect tampering, where that matters (anti-cheat, platform requirements).
- **Encryption** is sometimes required by platforms or publishers. The keys belong to the build pipeline and are
  provisioned per build, never committed with the project's files.

## Chunks: installing and streaming

Content can be split into **chunks** with priorities: the chunks needed to start come first, so the application
can start while the rest downloads ("play while installing"). Large worlds use the same idea: each region's content
in its own chunk, streamed on demand ([The IO scheduler and streaming](04-scheduler-and-streaming.md)).
